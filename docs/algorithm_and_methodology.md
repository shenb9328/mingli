# 命理数据库 V3.2：数据模型、算法与校验方法

## 1. 目标

本项目不是把八字口诀堆成一个“吉凶词典”，而是建立一个可追溯、可复算、可审计的规则系统。

核心原则：

1. **文本与解释分离**：古籍原文、现代解释、程序规则不混在同一字段。
2. **来源与证据等级分离**：有来源不等于已经完成扫描页校勘。
3. **规则分层**：月令、日主、藏干、十神、旺衰、格局、调候、合冲刑害、病药、岁运分别计算。
4. **先结构、后结论**：任何单一神煞、合冲或十神不得直接覆盖原局结构。
5. **禁止伪精确**：数据库宁可标记“异文/待核”，也不把现代整理表伪装成古籍原文。
6. **不使用固定吉凶分数**：如果未来加入数值评分，必须明确标记为 heuristic，而不是古典规则。

## 2. 总体计算管线

```
输入四柱
  ↓
历法层：年/月/日/时干支
  ↓
月令层：月支、节气、司令藏干
  ↓
日主层：日干、阴阳、五行
  ↓
藏干层：十二地支藏干及本/中/余气
  ↓
十神层：以日干为参照映射
  ↓
旺衰层：月令 + 根气 + 透干 + 生扶泄耗制化
  ↓
格局层：月令提纲 → 格局候选 → 成败救应
  ↓
用神层：月令用神、顺逆、变化
  ↓
调候层：日主 × 月令 120格矩阵
  ↓
关系层：合、冲、刑、害、破、会局
  ↓
病药层：找失衡点 → 找制化药
  ↓
大运层：运支/运干加入后重新计算
  ↓
流年层：年柱加入后再次重新计算
  ↓
综合解释
```

## 3. V3.2 的核心算法

### 3.1 调候矩阵

《穷通宝鉴》按“十干×十二月”组织调候内容，因此本库固定建立 **10×12=120** 个格位，而不是只保存若干口诀。

每个格位至少包含：

- `day_master`：日主
- `month_branch`：月令
- `tiaohou_priority`：调候优先序
- `primary_use`：首要调候对象
- `secondary_use`：次要对象
- `twelve_growth_stage`：十二长生状态
- `source_refs`
- `evidence_level`
- `verification_status`
- `notes`

这里的“优先序”只是《穷通宝鉴》提要层的结构化表达，**不是最终用神判定**。

### 3.2 十二长生

十二长生作为独立特征计算，不直接等价于现代“强弱分数”。

算法：

1. 根据日主天干查 `twelve_growth.json` 对应序列。
2. 在月令支上查找位置。
3. 得到“长生、沐浴、冠带、临官、帝旺、衰、病、死、墓、绝、胎、养”之一。
4. 该状态只进入旺衰辅助层，不能单独决定格局或吉凶。

### 3.3 十神

十神由三个条件共同决定：

- 五行生克方向；
- 与日干同/异五行；
- 阴阳同/异。

因此程序应由关系函数计算，而不是给每个日主复制一套硬编码表。

### 3.4 旺衰

建议采用“证据集合”而不是简单加减分：

- 月令得令；
- 同类根气；
- 生扶来源；
- 泄耗；
- 克制；
- 透干；
- 合化/冲战等结构变化。

如果以后为了机器检索需要数值化，可以另建 `heuristic_strength_model.json`，不得把数字写进经典规则本身。

### 3.5 格局

格局候选优先从月令提纲产生：

```
月令 → 藏干 → 透干 → 十神 → 格局候选
```

然后检查：

- 是否有相应透干；
- 是否有生扶；
- 是否被冲破、混杂或制化；
- 是否符合该格的成败条件。

“出现正官/七杀/财/印”等十神，不等于自动成格。

### 3.6 用神与调候必须分层

这是数据库最重要的防错规则之一：

- **格局用神**：解决结构成败；
- **调候**：解决寒暖燥湿；
- **扶抑**：解决日主及五行失衡；
- **通关**：解决两行相战；
- **病药**：寻找具体失衡点及制化手段。

这些层可以共同指向同一五行，但不能互相偷换。

## 4. 证据等级

- E0：无可靠证据，不进入可信规则库
- E1：二手现代资料
- E2：多个可靠数字文本交叉核对
- E3：可追溯历史版本，但尚未逐页扫描校勘
- E4：扫描页逐字核验
- E5：两种以上历史扫描版本对校

当前 V3.2 的120格调候矩阵统一采用 **E2**。

原因：调候提要已能通过多份数字文本交叉验证，但尚未逐格完成历史刻本页面级校勘，因此不冒充 E4/E5。

## 5. 为什么采用“120格”而不是“口诀列表”

如果只保存：

> 甲木冬月喜火

程序无法回答：

- 是寅月还是子月？
- 是甲还是乙？
- 火是主药还是佐药？
- 是否还有水、金、木等条件？
- 该规则属于哪一古籍体系？
- 该规则的证据等级是什么？

120格矩阵把“日主”和“月令”显式化，使规则可以被程序稳定检索，也可以与其他规则层做交叉计算。

## 6. 当前版本的边界

本版本故意不做：

- 把调候主药直接转换成“吉/凶”；
- 把十二长生转换成固定分数；
- 把神煞作为核心判定；
- 用现代人格/职业标签冒充古典原文；
- 把徐乐吾等后世评注直接标成原作者文本；
- 用一个来源覆盖全部版本差异。

## 7. 后续校勘路线

### E2 → E3

给每个经典条目绑定具体数字底本、卷次、章节。

### E3 → E4

逐条定位历史扫描版页码，并人工/视觉核对字符。

### E4 → E5

对关键条目至少使用两种历史扫描版本做异文校勘。

优先级：

1. 《穷通宝鉴》十干十二月调候
2. 《子平真诠》用神、顺逆、变化、格局高低
3. 《滴天髓》体用、旺衰、病药
4. 《渊海子平》月令、十神、格局
5. 《三命通会》神煞及子平汇编条目

## 8. 数据库质量原则

任何新增规则必须回答五个问题：

1. **谁说的？** author/source
2. **在哪本书？** source_ref
3. **原文还是解释？** text_layer
4. **证据有多强？** evidence_level
5. **程序如何使用？** rule/graph node/heuristic

回答不了其中任何一个问题，就不能把它作为高可信经典规则直接进入核心库。
